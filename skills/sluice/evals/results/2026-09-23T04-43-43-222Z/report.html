They look alike (both are opaque strings in a header), but they point in opposite directions and do different jobs.

## Request ID: "which call was this?"

- **Unique for every HTTP call**, including retries. If you retry three times you get three request IDs.
- Usually **the server generates it** and returns it in the response (Stripe's `Request-Id`, AWS's `x-amzn-RequestId`). Some systems also let the client send one for tracing (`X-Request-ID`, W3C `traceparent`).
- **It doesn't change behaviour.** It's for observability: correlating logs, sending support "here's request `req_abc123`, why did it 500?", and distributed tracing.
- **When it earns its place:** always. It costs almost nothing and makes every incident easier to debug.

## Idempotency key: "which intent was this?"

- **The same value across every retry of one logical operation.** Three retries of "charge Alice $50 for order 789" all carry the same key.
- **The client generates it**, because only the client knows that two calls are the same attempt.
- **It does change behaviour.** The server stores the key with the result. If the key comes in again, the server returns the stored response and doesn't run the operation a second time.
- **When it earns its place:** any non-idempotent, side-effecting call where a duplicate causes real harm, like creating charges, refunds, transfers, payouts, or orders. You don't need it on GET/PUT/DELETE, which are naturally idempotent, and it's rarely worth it on cheap, harmless creates.

## Why payments need both

The classic failure: you POST a charge, the server processes it, and the connection drops before you get the response. You don't know whether it worked.

- Retrying without an idempotency key risks charging the customer twice.
- Retrying with the same key returns the original charge if it went through, or processes it now if it didn't.
- The request IDs on those two attempts let you see in the logs exactly what happened on each one.

So: **one idempotency key per operation, one request ID per attempt.**

## Implementation details that matter

1. **Derive the key from the business intent, or persist it before the first attempt.** For example, use `order_789_charge`, or a UUID saved alongside the order. Generating a fresh UUID inside your retry loop defeats the purpose.
2. **Scope keys** per account or API key, and expire them after a set time (Stripe keeps them for 24h).
3. **Reject a reused key with a different payload.** Stripe returns an error rather than silently replaying. Otherwise a client bug can come back looking like a success.
4. **Handle concurrent duplicates.** If a second request arrives while the first is still running, return a 409 (or lock and wait). Don't run both.
5. **Decide which outcomes you store.** Usually you replay successes and deterministic 4xx errors. Transient 5xx errors often aren't stored, so a retry can actually retry.
6. **Record the key atomically with the side effect,** in the same transaction if you can. If you write the key and then crash before charging, or charge and crash before writing the key, you've reopened the double-charge window.

**Rule of thumb:** use request IDs everywhere for debugging. Add idempotency keys wherever a retry could move money or create something twice.

import { DEFAULT_TARGET, TARGETS } from "./targets.js";

const STEPS = ["build", "upload", "activate"];

export function deploy(args, log = console.log, targets = TARGETS) {
  const dryRun = args.includes("--dry-run");
  const target = resolveTarget(args, targets);

  for (const step of STEPS) {
    log(`-> ${step}`);
    if (!dryRun) {
      target[step]();
    }
  }

  log(dryRun ? "dry run: 3 steps skipped" : "deployed: 3 steps");
}

function resolveTarget(args, targets) {
  const i = args.indexOf("--target");
  const name = i === -1 ? DEFAULT_TARGET : args[i + 1];
  const target = Object.hasOwn(targets, name) ? targets[name] : undefined;
  if (!target) {
    throw new Error(`unknown target: ${name}`);
  }
  for (const step of STEPS) {
    if (typeof target[step] !== "function") {
      throw new Error(`target ${name} has no ${step} step`);
    }
  }
  return target;
}
