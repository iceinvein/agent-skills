I've written the design to `docs/specs/2026-09-23-shared-rate-limiter.md`. I haven't written any code or the task plan yet; both wait for your sign-off on the design.

**The shape:**
- **One chokepoint.** All three callers already go through `call()` in `src/upstream/client.js`, so the limiter goes inside it. Each caller only adds a `caller` tag.
- **Token bucket.** It stores two numbers, refills when a caller asks, and needs no background process.
- **Shared counters behind a store interface.** The limiter only needs one operation from the store: an atomic "refill and take". I'd use SQLite through the built-in `node:sqlite`, which adds no dependencies (the repo has none today). A file lock makes it safe across processes. Redis is the alternative if the callers run on different machines.
- **Each caller behaves differently when the budget runs out:**
  - The CLI waits, up to 60s.
  - The worker waits, but can't use the last 20% of the bucket, so a backfill can't starve live traffic.
  - The webhook waits up to 2s, then returns `503` with a `Retry-After` header.
- **An upstream 429 pauses all three.** When upstream rejects a call, the store marks the bucket empty for every process until the retry time. Otherwise each process would hit the 429 separately.
- **Proof that the counters are really shared:** a test starts several `node` processes against one database file and checks they never take more than the budget allows in total.

**One question decides the store:** do the CLI, webhook handler and worker all run on the same host? If yes, SQLite with no new dependencies (my recommendation). If no, Redis, and we'd need an instance all three can reach.

I'll also need the upstream's actual rate and burst limits to set the defaults. Once you answer and approve the design, I'll write the task plan for a second review before starting.
