They answer different questions. An **idempotency key** tells the server that a request is the same operation as an earlier one, so it shouldn't run twice. A **request ID** records which HTTP call something happened on, so you can trace it later.

## Idempotency key: "don't do this twice"

- **Who creates it:** the client, before the first attempt.
- **Lifetime:** one *logical operation*. You reuse the same key on every retry of that operation.
- **What the server does with it:** it stores the key along with the result of the first request that finished. If the same key arrives again, the server returns the stored response and doesn't run the operation again. Good implementations also:
  - lock the key while the first request is still running, so two concurrent retries can't both execute
  - fingerprint the request body and reject a reused key that comes with different parameters (Stripe returns a 400 or 409 for this)
  - expire keys after a set window (Stripe uses 24h)
- **Why it matters:** your client sends "charge $50", the connection times out, and you can't tell whether the charge went through. Without a key, retrying might charge the customer twice. With a key, retrying is always safe.

## Request ID: "which call was this?"

- **Who creates it:** usually the server, which returns it in a header like `Request-Id` or `X-Request-Id`. Sometimes the client sends one as a correlation ID.
- **Lifetime:** one *HTTP attempt*. Every retry gets a new one.
- **What the server does with it:** nothing that affects behavior. It goes into logs, traces, and error reports.
- **Why it matters:** debugging and support. "Request `req_8f3a…` returned a 500" lets the provider find that exact call in their logs.

## Side by side

| | Idempotency key | Request ID |
|---|---|---|
| Scope | Logical operation | Single HTTP attempt |
| Same across retries? | **Yes**, that's the point | **No**, each attempt is distinct |
| Changes server behavior? | Yes, deduplicates | No, only observability |
| Generated by | Client | Usually server |
| Needs server-side storage? | Yes, key → response, with a TTL | Only in logs |

If one charge is retried three times, you get one idempotency key and three request IDs. All three attempts return the same charge, but each attempt has its own trace.

## When each one earns its place

**Use idempotency keys on any non-idempotent write that has side effects:** creating charges, refunds, transfers, payouts, or anything else that moves money or sends something to the outside world. GET, PUT, and DELETE are already idempotent by HTTP semantics, so they rarely need one. POST is where you need it.

A few practical tips:
- **Generate the key from something stable in your own domain, or save it before the first attempt.** For example, derive it from `order_id + "charge"`, or write a UUID to your DB alongside the pending order. If you generate a fresh UUID on every attempt, it does nothing, because each retry looks like a new operation.
- **Choose the key's scope on purpose.** "Retrying this exact charge" should reuse the key. "The customer clicked pay again after a decline" is a new attempt and should get a new key.
- **Don't reuse a key with a different amount.** Good servers reject it. Weaker ones silently return the old result.

**Use request IDs everywhere.** They cost almost nothing. Log the provider's request ID next to every outbound call, especially failed ones, because support will ask for it first. If you're building the API, return one on every response, including errors.

## Common mistake

Treating a request ID as an idempotency key. It's unique per attempt, so it can never match a retry and never deduplicates anything. And if a server did deduplicate on request IDs, a client that happened to reuse one would see a new operation silently dropped.

In short, use the idempotency key to make retries safe and the request ID to debug what happened. Most payment integrations need both.
