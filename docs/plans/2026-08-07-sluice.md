# Sluice Implementation Plan

> **For agentic workers:** implement this plan task-by-task, dispatching a fresh
> agent per task and reviewing between tasks. Steps use checkbox (`- [ ]`) syntax
> for tracking. This plan does not require the superpowers plugin to execute and
> derives no text from it. All prose is original, so the skill carries no
> third-party licence obligation.

**Goal:** Ship `skills/sluice/`, a Claude Code skill that routes work by change shape into four channels and applies only the rules each channel needs.

**Architecture:** One skill directory. `SKILL.md` is an always-loaded-on-invoke router (~785 tokens) carrying the channel table, each rule as a single line, and the deep-channel execution recipe. Six `references/*.md` files carry the expensive material (rationalization tables, worked examples, the plan format, the dispatch rules) and are read only on friction. A `claudeHookDirective` in `skill.json` puts a ~20-token routing directive in every session via the installer's SessionStart hook.

**Tech Stack:** Markdown prose, JSON manifests, Bun (`bun run skill:audit`, `bun run build:index`). No new dependencies. No runtime code.

**Spec:** `docs/specs/2026-08-07-sluice-design.md`. Read it before Task 1.

## Global Constraints

- Skill directory name, `skill.json` `name`, and `SKILL.md` frontmatter `name` must all be exactly `sluice`. The audit errors on any mismatch (`scripts/audit-skills.ts`, "name != dir").
- `skill.json` `description` and the `skills/index.json` entry `description` must be byte-identical. Regenerate with `bun run build:index`; never hand-edit `index.json`.
- `SKILL.md` YAML frontmatter must be under 1024 characters.
- No em dashes anywhere in `skill.json` `description` (the audit emits INFO) or in any prose in this skill. Use commas, parentheses, or separate sentences.
- **Cross-reference lint trap:** the audit errors on any backticked kebab-case token preceded by `use`, `see`, `→`, `->`, `route to`, or `signal for` that is not an existing skill directory. Always write reference files as `references/<name>.md` (the `/` and `.` prevent the pattern from matching). Never write `` see `test-first` ``.
- New skills must not gain `applies` or `quick` fields in `index.json`. Those fields bind a skill into the `improve-my-codebase` routing table, which the audit then requires to stay in sync. `bun run build:index` omits them for new skills; leave it that way.
- `"tools": ["claude"]` only. No Cursor, Codex, or Gemini install targets.
- Version `1.0.0`.
- Token budgets are measured as `wc -c` divided by 4. `SKILL.md` under 900 (measured at 785 for the text in Task 2; the spec's original ~600 estimate was optimistic and was revised rather than met by cutting content that earns its place). Reference files within 20% of their spec targets.
- Every task ends with `bun run skill:audit` reporting zero ERR for `sluice`.
- Channel names are exactly `bypass`, `fast`, `main`, `deep`. Lowercase in prose.
- **All prose is original, and this is checked. Originality means expression,
  not ideas.** Copyright covers how something is said, not what is said. These
  rules state ordinary engineering knowledge, and every one of them has been
  written down before; making the same true claim as an existing text is
  required, not a defect.

  What is forbidden: reproducing another text's sentences, its distinctive
  examples, its section structure, or a recognisable paraphrase of a specific
  passage. A synonym swap over someone else's sentence is copying.

  What is permitted, and expected: asserting the same underlying facts about
  testing, debugging, and review that any competent source would assert. A
  reviewer who rejects a sentence solely because the claim also appears
  elsewhere has applied the wrong standard, and that rejection is not a defect
  to fix.

  Where a brief's own wording sits close to existing phrasing on the same topic,
  treat the brief as naming the claim, not supplying the words. The underlying ideas (test first, root cause before fix, verify
  before claiming) are common engineering practice and free to state; the
  specific wording must be yours. This keeps the skill free of third-party
  licence obligations, so there is no NOTICE file and nothing to attribute.
- **Write to the budget, not to a source.** Each reference file below is
  specified by the claims it must make, not by what to keep or cut from
  something else. If a required claim will not fit the budget, say so in the
  task report rather than dropping it silently.

---

# Sluice

A sluice sorts material by size into channels and meters what flows through.
Same here: pick the channel the change needs, pay for nothing else.

## Route first

Pick a channel from the change's shape, state it in one line, then proceed. The
announcement is how your human partner redirects you without being asked.

| Channel | Signal | Rules | Say |
|---------|--------|-------|-----|
| `bypass` | No code change: a question, an explanation, a read | none | nothing, just answer |
| `fast` | Existing interfaces, one subsystem | test-first, verify | "Fast channel. Test first, then implement." |
| `main` | Adds an interface, or crosses subsystems | + agree intent, review before merge | "Main channel, new interface. Agreeing the shape first." |
| `deep` | Several subsystems, or a plan was asked for | + written design and plan | "Deep channel, several subsystems. Design before code." |

`bypass` says nothing. A question that gets announced at stops being a question.

**`root-cause` is not channel-assigned.** Any bug, test failure, or unexpected
behaviour triggers it, in every channel including `bypass`.

## The rules

One line each. Read the reference only on friction: the moment you notice
yourself wanting to skip the rule, or arguing that this case is different.

- **Agree intent** before building. One question at a time. Propose approaches
  with a recommendation, not a survey. `main` agrees in a message, `deep` writes
  it down. `references/intent.md`
- **Test first.** Write the failing test, watch it fail, then the minimal code.
  If you did not watch it fail you do not know what it tests.
  `references/test-first.md`
- **Root cause** before fix. Symptom fixes are failure. Three failed fixes means
  the architecture is wrong, not your hypothesis. `references/root-cause.md`
- **Verify** before claiming. Run the command in this turn, read the output,
  then make the claim. Confidence is not evidence. `references/verify.md`
- **Review** before merge. Dispatch a reviewer with fresh context and hand it the
  diff as a file, so it lands in their context and not yours.
  `references/review.md`
- **Finish** deliberately. Green suite first, then let your human partner pick
  merge, PR, or leave it. Never pick for them. `references/finish.md`

## Changing channel

Escalate out loud. A `fast` task that turns out to need a new interface becomes
`main`, and you say so. Finishing quietly in the wrong channel is the failure
this prevents; the same goes for dropping to a shallower one. Explicit
instruction wins: "just do it" collapses to `fast`.

## Deep channel

Design to `docs/specs/YYYY-MM-DD-<topic>.md`, plan to
`docs/plans/YYYY-MM-DD-<topic>.md`, unless the repo has a convention or your
human partner states a preference. Get the design signed off before code.

Then read `references/deep-channel.md` for the plan format, the dispatch rules,
and when a task actually needs a reviewer. Two that catch people out: never run
two implementers at once, and review is tiered, not automatic.

- [ ] **Step 2: Write `references/test-first.md`**

Target ~400 tokens (under 1800 chars). Original prose. This rule fires in every channel except `bypass`.

Required content:
- Write one minimal failing test, watch it fail, write the minimal code, watch it pass.
- Watching it fail is the load-bearing step: a test that never failed proves nothing about what it catches.
- If the test passes on first run, it is testing existing behaviour. Fix the test, not the code.
- Before writing a test, name the production change that would make it fail. If you cannot, the test asserts nothing.
- Assert on real behaviour, never on mock behaviour.
- Exceptions worth asking about: throwaway prototypes, generated code, config files.
- Keep test-only helpers in the test files. A production class that grows a method existing only so a test can reach inside it has had its design bent by the test.
- Understand what a dependency actually does before mocking it. A mock that does not match the real side effects produces a green test over broken code.
- The friction line: "I will test after." Make exactly one point here, chosen by you, and make it one this file has not already made. The watch-it-fail claim is stated earlier in the file, so restating it here is redundancy, not emphasis. Do not enumerate several reasons in sequence; a single sharp observation is the requirement. Standard arguments about testing after the fact are widely rehearsed, so if the sentence you draft could sit unchanged in someone else's tutorial, draft a different one.

### Task 4: The during-and-after rules

The three rules that fire while work is happening or before it is called done.

**Files:**

**Interfaces:**

- [ ] **Step 1: Write `references/root-cause.md`**

Target ~360 tokens (under 1600 chars). Original prose. Trigger-based, so it fires in every channel including `bypass`.

Required content:
- No fix without root cause investigation first.
- Phase 1, investigate: read the error completely, reproduce it reliably, check what changed recently, trace the bad value back to where it originates. Fix at the source, not where it surfaced.
- Phase 2, compare: find working code that is similar and list every difference, however small.
- Phase 3, hypothesize: state one hypothesis, test it with the smallest possible change, one variable at a time.
- Phase 4, fix: write the failing test that reproduces it first, make one change, verify.
- Three failed fixes means the architecture is wrong. Stop and raise it rather than attempting a fourth.
- State plainly that this rule is trigger-based and applies in every channel, `bypass` included.
- Two named techniques, one line each. Defense in depth: once the root cause is fixed at its source, add validation at the layers that let the bad value through, so the next variant fails loudly instead of silently. Condition-based waiting: a test that sleeps for a fixed duration is a test that will flake, so poll for the condition the test actually depends on and fail on a timeout.
- The friction line: "it is probably X, let me just try that." Seeing the symptom is not understanding the cause.

- [ ] **Step 2: Write `references/verify.md`**

Target ~250 tokens (under 1200 chars). Original prose. This rule fires in every channel except `bypass`.

Required content:
- No completion claim without fresh verification evidence. If you did not run the command in this turn, you cannot say it passes.
- The gate: identify the command that proves the claim, run it in full, read the output and exit code, then make the claim with the evidence.
- A short claim-to-evidence table covering: tests pass needs the test output with zero failures; build succeeds needs exit 0, not a clean linter; bug fixed needs the original symptom retested; a subagent finished needs the VCS diff, not the agent's own report.
- Regression tests need the red-green check: revert the fix, confirm the test fails, restore, confirm it passes.
- The rule covers paraphrase and implication, not just the exact words. Expressing satisfaction before verifying is the same violation.
- The friction line: "it should work now." Run it.

- [ ] **Step 3: Write `references/review.md`**

Target ~350 tokens (under 1600 chars). Original prose. This rule fires in the `main` and `deep` channels only.

Required content:
- When: before merge, and after any change large enough to have earned the `main` or `deep` channel.
- Hand the reviewer a file, never a pasted diff. `git diff <base> <head> > <file>` then give the path. The diff belongs in the reviewer's context, not in yours.
- Give the reviewer: what was built, what it was supposed to do, and the diff path. Never your session history.
- Use the real base commit, not `HEAD~1`, which silently drops every commit but the last of a multi-commit change.
- Do not pre-judge. Never tell a reviewer not to flag something. If you believe a finding is wrong, let it be raised and then argue it.
- Severity handling: fix Critical and Important before proceeding, record Minor and carry it to the final review.
- Receiving: verify a finding against the codebase before implementing it, and push back with technical reasoning when it is wrong. No performative agreement.
- Handling findings: send them back to the agent that wrote the code, since its context is intact. Cap at three rounds. Findings still open after three are structural, so stop and report rather than starting a fourth.
- Two buckets, not three: fix it now, or record it and move on. Recorded findings surface at the final review. Severity grades and adjudication procedures cost more to run than the findings they sort.
- Verify a small fix by reading the fix diff and confirming the covering test ran. Dispatch a fresh re-review only when the fix changed logic substantially.
- Never fix findings yourself when coordinating. Controller fixes skip review entirely and burn the context you need for the remaining tasks.
- The friction line: "I will just read the diff myself." That burns the context you need to keep coordinating, and self-review is not review.

Target ~750 tokens (under 3100 chars). Original prose. Covers three things: the plan format, the dispatch rules, then the review policy. Only the deep channel ever loads it, so the budget is looser than the router's.

Required content:
- A plan opens with Goal, Architecture, and a Global Constraints section. Global
  Constraints holds project-wide requirements with exact values, and every task's
  requirements implicitly include it.
- Each task states its exact file paths: what it creates, what it modifies, what
  it tests.
- Each task carries an Interfaces block with Consumes and Produces, holding exact
  signatures. State why it exists: the implementer sees only its own task, so this
  block is the only way it learns the names and types its neighbours use. This is
  the part that makes a context-free dispatch work, so it is not optional.
- Steps are checkboxes. A step says what to do and what result proves it worked.
- Steps do not spell out the test-first ritual; `references/test-first.md` owns
  that cycle and repeating it per task is noise.
- Include code only where the exact text matters: signatures, magic strings, test
  cases, commands. Prose deliverables are specified by the claims they must make
  and their budget, not by reproducing them.
- No placeholders. No TBD, no "add appropriate error handling", no "similar to
  Task N", no reference to a type or function that no task defines. Each of these
  is a plan failure, not a stylistic preference.

Include a compact skeleton showing the header, Global Constraints, and one task
with Files, Interfaces, and checkbox steps.

Then the dispatch rules:
- One `TaskCreate` entry per task, marked in progress and complete as you go.
  That state outlives compaction; your memory of what you dispatched does not.
- A fresh agent per task, given the task text and never your session history.
  A dispatch describes one task, not the session so far.
- **Never run two implementers at once.** They collide in the same files.
- Fan out freely for work that does not write: independent investigations,
  unrelated failures in separate subsystems, searching several areas at once.
  One agent per independent question, dispatched in a single message so they run
  concurrently. The test is whether two agents could touch the same file.
- Work in an isolated workspace before starting a multi-task plan. Use the
  harness's own worktree tool if it has one rather than running `git worktree`
  behind its back, and never start on main without your human partner saying so.
- Match the model to the task: cheap for mechanical work, stronger for design
  judgment and for the final review.

Then the review policy, which is the part that decides whether a plan finishes
in an afternoon or a week. State the cost up front: a review costs roughly what
the implementation cost, so reviewing every task unconditionally doubles the
plan. Spend it where it changes an outcome.

Spec compliance is free and always done: you hold the plan, so check the task
produced the `Produces` entries in its Interfaces block and touched only its
declared `Files`. That is a `git diff --stat` read, not a dispatch. What needs a
fresh agent is quality judgment.

Include this table:

| Task shape | Review |
|------------|--------|
| Only touched files it created, tests pass, matches its Interfaces block | No dispatch. Read the diff stat yourself. |
| Modified existing code, or later tasks build on it | One reviewer dispatch |
| Auth, data, money, concurrency, or the plan flags it | One reviewer dispatch, stronger model |

Then the fix policy:
- `git diff <base> <head> > <file>` and hand the reviewer the path. Base is the
  commit before the task started, never `HEAD~1`, which silently drops every
  commit but the last of a multi-commit task.
- Findings go back to the agent that wrote the code; its context is intact.
- **Verify small fixes yourself.** Read the fix diff and confirm the covering
  test the fixer named actually ran. Re-dispatch a scoped re-review only when
  the fix changed logic substantially. Re-review dispatches are most of what
  makes a review loop expensive, and most fixes are too small to earn one.
- At most three fix rounds. Still open after three is structural: stop, say
  what is unresolved, and let your human partner decide.
- **A finding that survives two rounds may be a defect in the acceptance
  criterion, not the work.** Before dispatching a third, state the criterion
  plainly and ask whether any output could satisfy it. An unfalsifiable
  criterion (one that rejects every attempt for the same reason) never
  converges, and the writing degrades each round as it contorts to pass a test
  with no passing answer. Fixing the criterion is the controller's call and it
  is not something the reviewer can raise, since the reviewer is the one
  applying it.
- Never fix findings yourself while coordinating. That skips review entirely and
  burns the context the remaining tasks need.
- Two buckets for findings, not three: fix it now, or write it in the task entry
  and move on. Anything recorded goes to the final review. No severity grades,
  no adjudication procedure.
- The final review is scoped to what per-task review could not see: cross-task
  integration, and anything recorded and deferred. It does not re-read lines a
  per-task review already cleared.
