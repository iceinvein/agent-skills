# Sluice Implementation Plan

> **For agentic workers:** implement this plan task-by-task, dispatching a fresh
> agent per task and reviewing between tasks. Steps use checkbox (`- [ ]`) syntax
> for tracking. This plan deliberately does not require the superpowers plugin to
> execute, since the skill it builds replaces it and the design calls for
> superpowers to be disabled.

**Goal:** Ship `skills/sluice/`, a Claude Code skill that routes work by change shape into four channels and applies only the rules each channel needs.

**Architecture:** One skill directory. `SKILL.md` is an always-loaded-on-invoke router (~600 tokens) carrying the channel table, each rule as a single line, and the deep-channel execution recipe. Six `references/*.md` files carry the expensive material (rationalization tables, worked examples, the plan template) and are read only on friction. A `claudeHookDirective` in `skill.json` puts a ~20-token routing directive in every session via the installer's SessionStart hook.

**Tech Stack:** Markdown prose, JSON manifests, Bun (`bun run skill:audit`, `bun run build:index`). No new dependencies. No runtime code.

**Spec:** `docs/specs/2026-08-07-sluice-design.md`. Read it before Task 1.

## Global Constraints

- Skill directory name, `skill.json` `name`, and `SKILL.md` frontmatter `name` must all be exactly `sluice`. The audit errors on any mismatch (`scripts/audit-skills.ts`, "name != dir").
- `skill.json` `description` and the `skills/index.json` entry `description` must be byte-identical. Regenerate with `bun run build:index`; never hand-edit `index.json`.
- `SKILL.md` YAML frontmatter must be under 1024 characters.
- No em dashes anywhere in `skill.json` `description` (the audit emits INFO) or in any prose in this skill. Use commas, parentheses, or separate sentences.
- **Cross-reference lint trap:** the audit errors on any backticked kebab-case token preceded by `use`, `see`, `→`, `->`, `route to`, or `signal for` that is not an existing skill directory. Always write reference files as `references/<name>.md` (the `/` and `.` prevent the pattern from matching). Never write `` see `test-first` ``.
- New skills must not gain `applies` or `quick` fields in `index.json`. Those fields bind a skill into the `improve-my-codebase` routing table, which the audit then requires to stay in sync. `bun run build:index` omits them for new skills; leave it that way.
- `"tools": ["claude"]` only. No Cursor, Codex, or Gemini install targets.
- Version `1.0.0`.
- Token budgets are measured as `wc -c` divided by 4. `SKILL.md` under 800. Reference files within 20% of their spec targets.
- Every task ends with `bun run skill:audit` reporting zero ERR for `sluice`.
- Channel names are exactly `bypass`, `fast`, `main`, `deep`. Lowercase in prose.
- **Source material is snapshotted, not read live.** Every superpowers file this

# Sluice

A sluice sorts material by size into separate channels and meters how much flows
through. This does the same to work: pick the channel the change actually needs,
and pay for nothing else.

## Route first

Pick a channel from the change's shape, state it in one line, then proceed.
The announcement is the point: it is how your human partner redirects you without
being asked to confirm anything.

| Channel | Signal | Rules | Say |
|---------|--------|-------|-----|
| `bypass` | No code change: a question, an explanation, a read | none | nothing, just answer |
| `fast` | Existing interfaces, one subsystem | test-first, verify | "Fast channel. Test first, then implement." |
| `main` | Adds an interface, or crosses subsystems | + agree intent, review before merge | "Main channel, new interface. Agreeing the shape first." |
| `deep` | Several subsystems, or a plan was asked for | + written design and plan | "Deep channel, several subsystems. Design before code." |

`bypass` says nothing. A question that gets announced at stops being a question.

**`root-cause` is not channel-assigned.** Any bug, test failure, or unexpected
behaviour triggers it, in every channel including `bypass`. Channels size the
process around a *change*; a bug earns investigation wherever it surfaced.

## The rules

One line each. Read the reference only on friction, meaning the moment you notice
yourself wanting to skip the rule or arguing that this case is different. That
moment is what the references are written for.

- **Agree intent** before building. Ask one question at a time. Propose approaches
  with a recommendation, not a survey. `main` agrees in a message; `deep` writes
  it down. Full treatment: `references/intent.md`
- **Test first.** Write the failing test, watch it fail, then write the minimal
  code. If you did not watch it fail you do not know what it tests.
  Full treatment: `references/test-first.md`
- **Root cause** before fix. Symptom fixes are failure. Three failed fixes means
  the architecture is wrong, not your hypothesis.
  Full treatment: `references/root-cause.md`
- **Verify** before claiming. Run the command in this turn, read the output, then
  make the claim. Confidence is not evidence.
  Full treatment: `references/verify.md`
- **Review** before merge. Dispatch a reviewer with fresh context and hand it the
  diff as a file, so the diff lands in its context and not yours.
  Full treatment: `references/review.md`

## Changing channel

Escalate out loud. If a `fast` task turns out to need a new interface, say so and
move to `main`. Finishing quietly in the wrong channel is the failure this
prevents.

Dropping to a shallower channel mid-task needs the same announcement. Explicit
instruction from your human partner always wins: "just do it" collapses to `fast`
whatever the signal says.

## Deep channel

Write the design to `docs/specs/YYYY-MM-DD-<topic>.md` and the plan to
`docs/plans/YYYY-MM-DD-<topic>.md`, unless the repo already has a convention or
your human partner has stated a preference. Both override the default. Get the
design signed off before writing code. Plan format: `references/plan-template.md`

Then execute:

- One task per `TaskCreate` entry.
- Fresh `Agent` per task. Give it the task text, never your session history.
- `git diff <base> <head> > <file>`; hand the reviewer the path, never a pasted
  diff.
- Review each task before starting the next.

## Conflicts

Sluice cannot coexist with the superpowers plugin. Superpowers installs a
SessionStart hook mandating its brainstorming skill before any creative work,
which overrides this router on exactly the fast path it exists to open. Disable
superpowers before relying on sluice.
